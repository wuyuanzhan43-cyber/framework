# 注释规范

目标：让读者先知道“这段代码属于哪一层、谁拥有它、在哪个上下文调用”，
再读实现细节。注释解释**契约、所有权、并发和原因**，不复述代码。

代码注释统一使用中文；类型名、函数名、宏和硬件术语保留英文。文档与代码注释
使用同一语言，便于对照阅读。

## 1. 文件头

每个 `.c/.h` 文件开头使用同一结构，长度控制在 5~10 行：

```c
/*
 * fw/ring.c - 固定容量字节 FIFO。
 *
 * 层级：framework/core
 * 职责：在调用者缓冲区和静态存储之间复制字节。
 * 上下文：无内部锁；UART 端口在任务侧访问时关闭中断，其他用户必须自行串行化。
 * 依赖：fw/ring.h。
 */
```

- **层级**：`framework/core`、`components/protocol`、`app`、`port`、`board`、
  `project`、`test`。
- **职责**：一句话说明职责，不写实现步骤。
- **上下文**：任务/ISR 约束；没有特殊约束写“任务上下文”或“单所有者”。
- **依赖**：允许依赖的头文件/层，用来检查分层红线。
- 头文件的文件头放在 include guard 之前；`.c` 文件放在第一个 `#include` 之前。

## 2. 函数契约

公开函数、跨文件函数、ISR 回调和有副作用的 static 函数都要有块注释：

```c
/*
 * fw_ring_write - 把字节复制进 FIFO。
 *
 * 上下文：任务或 ISR，调用者需自行串行化。
 * 返回：实际复制的字节数；短计数表示 FIFO 已满。
 * 所有权：`data` 仅在本次调用期间借用。
 */
```

按需包含：

- **上下文**：`仅任务` / `仅 ISR` / `仅初始化` / `任意上下文`。
- **返回**：成功、背压、错误三种情况；错误时 `count` 的语义。
- **所有权**：缓冲区是否保留、谁负责释放、生命周期。
- **副作用**：修改哪些状态、是否发通知、是否触碰硬件。
- **前置条件**：初始化顺序、单实例、锁要求。

不要为 getter、一行转发函数写长篇注释；一句契约即可。

## 3. 结构体字段

每个非显然字段加行尾注释，写单位/所有权/生产者：

```c
typedef struct {
    uint8_t *storage;   /* 调用者拥有；容量为 capacity 字节 */
    size_t capacity;    /* 大于 0；不要求是 2 的幂 */
    volatile bool loss; /* ISR 置位；任务上报 EOVERFLOW 后清除 */
} fw_example_t;
```

- 时间写 `ms`；计数写 `帧数`、`字节数`；栈写 `32 位字`。
- ISR 与任务共享的字段标 `volatile`，并注明谁写、谁读。
- 指向调用者内存的指针必须写生命周期。

## 4. 宏与配置

- 宏上方一句用途；有合法范围或单位就写清楚。
- 配置项按组排列：`UART`、`DMA`、`IWDG`、`应用策略`。
- 不要给每个宏写重复的“定义 X”；写它约束什么。
- 构建开关要写默认值和回退方式。

## 5. 分区

长文件用短分隔线分区，最多 3~5 个区：

```c
/* -------------------------------------------------------------------------
 * 公开 API
 * ------------------------------------------------------------------------- */
```

推荐分区：`包含`、`私有辅助函数`、`公开 API`、`ISR / 回调`。
测试文件按测试组分区，不按每个断言分区。

## 6. 行内注释

只写“为什么”或“不变量”，例如：

```c
/* IRQ 是唯一生产者；任务排空 ring 时关闭中断。 */
mask = lock_rx();
```

不要写：

```c
/* 递增 i。 */  /* 错误：复述代码。 */
++i;
```

适合写行内注释的场景：

- 关键顺序（先排空再判超时、先置低再改方向）；
- 硬件/寄存器限制（DMA 不能访问 CCM、IRQ 优先级）；
- 绕开 HAL 行为的特殊处理；
- 状态转换和不变量；
- 魔数来源。

## 7. 测试注释

- 文件头写测试层次、运行方式、覆盖边界。
- 每个测试函数上方写：场景、输入、期望不变量。
- 不注释每一个 `CHECK`；用测试函数名和分组表达意图。
- 故障注入/违规端口必须写它故意违反哪条契约。

## 8. 维护规则

- 改行为时同步改注释；注释与代码不一致视为 bug。
- 不在注释里复制 README 的大段内容；需要时链接文档。
- 优先保留已有的高质量契约注释，只做结构化和补缺。
- 新增文件先套文件头，再写公开契约，最后写关键原因。
