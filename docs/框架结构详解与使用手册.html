01
Orientation

定位与阅读路径

先确认这套代码“是什么、不是什么”，再决定从哪里读。它刻意保持小而完整：功能不多，但边界、契约和验证链是完整的。

IS

它是什么

  • 一个契约驱动的最小闭环：UART 字节 → 协议 → 命令 → LED → 回复。
  • 同一份业务与协议代码可在 Host 和 STM32F407 上编译。
  • 静态分配、无 malloc，ISR/任务边界明确。
  • 有 Host 单测、接口 conformance、HIL 和目标硬件验证。
  • 默认启用 USART1 DMA，GCC 与 AC5 两条链都已上板验证。
IS NOT

它不是什么

  • 不是完整 RTOS 抽象层，也不是多任务设备框架。
  • 没有设备注册表、事件总线、日志服务、存储或 OTA。
  • 没有目标侧 17 条契约的完整 loopback conformance（已按需求跳过）。
  • DMA 映射目前只覆盖 USART1；AC6 尚未验证。
  • 不是“功能越多越好”的框架；扩展前先有需求与验收标准。

想快速使用：直接看 快速开始、构建、使用手册。
想理解设计：按 02 架构 → 03 数据通路 → 04 契约 顺序读。
想换板/扩展：看 06 端口、10 移植检查表、11 排障。

Architecture

分层架构：边界比功能重要

这套框架最重要的设计不是“抽象了很多层”，而是每条依赖边都被写清楚并可检查。层数不多，但边界稳定。

目录与职责

framework/app/assets/128×160 RGB565 示例图片只读常量，占用 Flash

WHY

可测试性

业务只依赖函数表，Host 端口可以模拟 UART、LED、时钟和故障，因而不需要板子就能验证分包、CRC、超时和背压。

WHY

可移植性

换芯片主要新增 framework/ports/ 与 framework/boards/；换 RTOS 主要新增 runtime port。协议与业务尽量不动。

WHY

可验证性

接口契约写在头文件里，Host conformance 能对端口逐条检查；板级只负责装配，不藏业务逻辑。

板级与项目装配

board_init() 只初始化时钟和 LED；串口由 board_console_init() 单独初始化。这样没有串口或没有 LED 的板子不会被“整体初始化失败”绑死。应用通过 fw_demo_init() 注入 stream、indicator、clock；main.c 只负责把对象接起来。

03
Data Path & Scheduling

数据通路与调度

接收和发送是两条独立的生产者/消费者链路。理解“谁拥有缓冲区、谁在 ISR、谁在任务”比记住函数名更重要。

RX 路径

  1. USART1 通过 DMA2_Stream2/Ch4 循环写入 256 B 缓冲。
  2. IDLE / HT / TC 事件把新位置差值复制到 512 B RX ring；跨 wrap 分两段复制。
  3. fw_demo_poll() 每轮最多读 rx_budget（默认 64）字节。
  4. 逐字节送入 parser；完整帧进入命令分发表。
  5. 处理完成后可直接在 RX ring 后继续下一帧；回复与上报不会互相覆盖 TX。

TX 路径

  1. handler 把回复编码到应用 TX 缓冲。
  2. fw_stream_write() 复制到端口 TX ring，返回 accepted。
  3. 端口 peek 一个 64 B chunk，启动 DMA/IT 发送。
  4. 完成回调消费已发送字节，并泵下一段。
  5. 调用者缓冲区不被保留；accepted 不代表物理线路完成。

轮询顺序：先排空，再判断，最后上报

顺序动作原因
1若 TX 未完成，先补发后缀不能在未完成时复用回复缓冲
2有界读取 RX（默认 64 B）保证每轮工作有上限，同时给 RX 机会
3仅当本轮没有读到任何字节，才判断半帧超时ring 里可能已有完整帧，先超时会误丢
4处理到期主动上报RX 先获得有界机会，上报每轮仍被检查
5回复发完后，同一轮可补发到期上报避免持续请求饿死上报，也不覆盖回复

fw_demo_next_wait_ms() 返回下一次需要 poll 的时间：TX 挂起返回 1 ms，上报/半帧超时到期返回 0，无截止时间返回 FW_DEMO_WAIT_FOREVER。UART RX/TX/error ISR 通过板级 hook 调用 vTaskNotifyGiveFromISR() 唤醒任务；空闲时最多每 1 秒兜底唤醒一次。

04
Contracts

核心接口契约

框架的价值首先体现在头文件里的约定。接口不是“函数签名”，而是“谁拥有缓冲区、错误后 count 怎么报、什么时候可以调用”。

DEVICE

fw_stream

字节流设备：UART、USB 字节流、Host 模拟器。包含 read/write 两个函数指针。

DEVICE

fw_indicator

输出设备：LED 或其它指示器。成功只代表“请求已记录”，不代表光学反馈。

SERVICE

fw_clock

单调毫秒时钟，按 232 回绕；两次读取间隔必须小于 231 ms。

Stream 读写约定

场景约定
read 空非阻塞，返回 FW_EAGAIN 且 count=0
read 容量端口绝不能写超过调用者 capacity
read 错误EIO/EOVERFLOW 表示连续性丢失；不返回数据，调用者复位 parser
write 接受返回真实 accepted 字节数；部分写入只重试后缀
write 错误错误时也要报告已经接受的字节；不能“接受了却报 0”
缓冲区write 返回后不保留调用者缓冲区；read 数据复制到调用者缓冲区
上下文单任务拥有设备；不在 ISR 中调用 poll/write；零长度操作成功
cframework/include/fw/io.h · 接口骨架
typedef struct {
    fw_status_t (*read)(void *ctx, uint8_t *data,
                        size_t capacity, size_t *count);
    fw_status_t (*write)(void *ctx, const uint8_t *data,
                         size_t length, size_t *count,
                         uint32_t timeout_ms);
} fw_stream_ops_t;

typedef struct {
    const fw_stream_ops_t *ops;
    void *ctx;
} fw_stream_t;

接口一致性套件：17 条契约

Host 端 tests/conformance 把契约拆成 17 条可执行检查，并额外构造 5 个故意违规的端口，确认套件真的会报错——一个从未拒绝过任何端口的测试套件没有证明力。

组条款证明什么
STREAM · 11READ.EMPTY / ORDER / BOUNDED / DRAINED空读、顺序、容量边界、排空后不凭空产生数据
STREAM · 11WRITE.COUNT / NORETAIN / PARTIALaccepted 真实、不保留调用者缓冲区、部分写入可重试
STREAM · 11WRITE.FAULT.PROGRESS / READ.FAULT.*错误时仍报告进度；流丢失时不返回数据
INDICATOR · 4OPS.COMPLETE / SET.OK / STATE / FAULT.NOSTATE设置成功可见；失败不改变状态
CLOCK · 2PRESENT / MONOTONIC时钟存在且不会看起来倒退

Host 套件使用内存模拟端口，证明的是“套件和 Host 适配器正确”。要把 17 条搬到 STM32 上，需要单独的测试固件、PA9↔PA10 loopback 和测试专用故障注入 hook。当前按需求跳过，因此目标端口还没有被这套套件逐条认证。

05
Protocol

协议与命令

一个短帧、幂等、无动态长度的二进制协议。它足以覆盖当前单设备场景，但没有版本号、ACK 或地址。

帧格式

A5PRE
5APRE
LEN0..32
SEQ1 B
CMD1 B
PAYLOADLEN bytes
CRC2 B · LE
CRC-16/CCITT-FALSE 覆盖 LEN / SEQ / CMD / PAYLOAD，不覆盖 A5 5A
CRC

校验参数

  • 多项式 0x1021
  • 初值 0xFFFF
  • 不反射、不异或输出
  • 测试向量："123456789" → 0x29B1
  • 低字节先发送
REPLY

回复规则

  • 请求 CMD 的 bit7=0
  • 回复 CMD = 请求 CMD | 0x80
  • 回复沿用请求 SEQ
  • 收到 bit7=1 的帧不再回复，避免互相应答
  • 命令幂等；无去重窗口

命令表

CMD名称请求负载正常回复
0x01PING空00 + "PONG"
0x02LED_SET00 关 / 01 开00
0x03STATUS空00 known state
0x04STATS空00 + 13 字节计数器
0x90EVENT_STATUS—主动上报，独立序号

STATS 负载布局

STATUS1 B · 0
FRAMESu32 LE
IO_ERRORSu32 LE

PING 请求：A5 5A 00 01 01 CRC；LED_SET(on)：A5 5A 01 02 02 01 CRC。完整示例与 CRC 可在 Host 演示程序和 HIL 脚本中看到。

当前协议没有版本、地址、ACK、重传和去重。单设备、短帧、幂等命令下足够；多设备或可靠传输需求出现时，应重新设计帧，而不是继续往当前格式里塞字段。

Ports & Board

端口、板级与 DMA

端口负责把统一接口接到具体平台；板级只决定“这块板子的引脚、时钟和外设实例”。DMA 是默认路径，IT 是可回退路径。

非阻塞 TX 的关键语义

  • write 只负责把字节复制进 TX ring，并返回 accepted。
  • 端口 peek 一个 chunk，启动 DMA 或 IT 发送；发送完成前不覆盖 chunk。
  • 完成回调消费已发送字节，并自动泵下一段。
  • ring 满时返回 EAGAIN，应用只重试后缀。
  • accepted 不代表物理线路完成；这是 io.h 契约的一部分。

错误分类

  • ORE：RX overrun，数据已丢，置 loss 并让 parser 复位。
  • FE/NE/PE：只丢一个坏字节，不整个清空 ring。
  • DMA 错误：记录 tx_errors，保留 ring 中的待发数据。
  • UART 端口有 rx_line_errors、rx_overrun_errors、tx_errors 计数器。

可选设备与能力查询

fw_demo_init() 只强制要求 stream 和 clock。没有 LED 的板子可以传空的 indicator，此时 LED_SET 会回复状态 3；board_capabilities() 暴露 indicator/console 是否存在。

FAULT

g_fault_dump

记录 CFSR/HFSR/MMFAR/BFAR、MSP/PSP 和 IPSR；GCC 的 HardFault 还会保存异常栈帧（含 faulting PC/LR）。当前位于 .bss，看门狗复位后会被清空。

8.4 新增一个命令

以新增 LED_TOGGLE 为例，按以下顺序改：

定义命令码

写 handler

加入分发表

补测试与文档

Host 单测覆盖正常/非法参数；HIL 增加对应步骤；README 协议表同步。

cframework/app/demo_app.c · 添加 handler 与表项
static void cmd_led_toggle(fw_demo_app_t *app,
                           const fw_message_t *request,
                           fw_message_t *reply)
{
    if (request->length != 0U) {
        reply->payload[0] = 1U;
        return;
    }
    /* 读取当前软件记录，翻转后写回 */
    if (fw_indicator_set(&app->indicator, !app->led_requested_on) == FW_OK) {
        app->led_known = true;
        app->led_requested_on = !app->led_requested_on;
    } else {
        reply->payload[0] = 3U;
    }
}

static const fw_demo_command_t command_table[] = {
    { FW_CMD_PING, cmd_ping },
    { FW_CMD_LED_SET, cmd_led_set },
    { FW_CMD_STATUS, cmd_status },
    { FW_CMD_STATS, cmd_stats },
    { FW_CMD_LED_TOGGLE, cmd_led_toggle }
};

8.5 新增一个设备/端口

定义 ops + ctx

按 fw_stream_ops_t 或 fw_indicator_ops_t 实现函数表；ctx 由你自己拥有，生命周期覆盖所有调用。

实现契约

read 非阻塞、容量受限、错误语义正确；write 报告真实 accepted、部分写入可重试、不保留调用者缓冲区。

接 Host conformance

用 tests/conformance 的适配器跑 17 条；缺少故障 hook 的条款会 SKIP，不会被伪装成通过。

板级装配

在 board_console()/board_indicator() 返回你的设备；不要在 app 里直接包含平台头。

目标验证

跑 HIL；如果更换的是 UART，确认 DMA/IT 路径、IRQ 优先级、缓冲容量和错误计数。

cstream port 骨架
static fw_status_t my_read(void *ctx, uint8_t *data,
                           size_t capacity, size_t *count)
{
    *count = 0U;
    if (ctx == NULL) return FW_EINVAL;
    /* 非阻塞：没有数据时返回 EAGAIN, *count = 0 */
    return FW_EAGAIN;
}

static fw_status_t my_write(void *ctx, const uint8_t *data,
                            size_t length, size_t *count,
                            uint32_t timeout_ms)
{
    *count = 0U;
    if (ctx == NULL) return FW_EINVAL;
    /* 报告真实 accepted；不要保留 data 指针 */
    return FW_OK;
}

static const fw_stream_ops_t my_ops = { my_read, my_write };

8.6 换板 / 换引脚 / 换时钟

  • 修改 framework/boards/stm32f407ve/board_config.h 的 LED、UART 实例、TX/RX 引脚、AF、IRQ 优先级和缓冲容量。

常见移植坑

CLOCK

改 PLL 忘记 tick

SystemCoreClock 变了但 SysTick/HAL tick 没重配，会表现为延时错误、超时异常、FreeRTOS 节拍错误。

IRQ

优先级不满足 FromISR

调用 FreeRTOS FromISR API 的 ISR，优先级数值必须不低于 configMAX_SYSCALL_INTERRUPT_PRIORITY。当前 UART/DMA 为 6，上限为 5。

DMA

映射抄错 stream

USART1 RX/TX 的 DMA stream/channel/IRQ 必须与参考手册一致；否则表现为“能编译、能发、收不到”或 NVIC 位不对。

BUFFER

把 CCM 给 DMA

STM32F4 的 DMA 不能访问 CCM。DMA 缓冲必须放在主 SRAM；当前设计已把 256 B RX 缓冲放在普通内存。

为什么 PA9/PA10 短接后看不到“结果”？

短接只是把 TX 接回 RX，不会自动运行测试。当前正常固件会收到自己发出的 0x90 帧，并按 bit7=1 忽略；PC 只能看到二进制帧，不会看到 PASS/FAIL。目标侧 conformance 需要单独的测试固件。

为什么建议复用已有 build 目录？

FetchContent 在配置阶段会检查并可能重新 clone 依赖。网络失败时，新的构建目录可能把现有依赖目录清空。复用已有目录或先确认网络/依赖完整性更安全。

DMA 失败会自动回退到 IT 吗？

只有在 DMA 初始化失败时，board 会重新用 IT 初始化。运行期 DMA 故障不会自动切换；需要时用构建开关回到 IT，并重新烧录。
